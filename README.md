# 期限くん

期限から逆算して、目標までにやることと進み具合を管理するモバイルファーストのPWAです。

Appleの[Human Interface Guidelines](https://developer.apple.com/jp/design/human-interface-guidelines/)を参考に、迷わず使えるシンプルな画面と、メインカラー`#26A79A`で設計しています。

**公開版:** [https://zuiken-code.github.io/DeadlineApp/](https://zuiken-code.github.io/DeadlineApp/)

## 主な機能

- 目標名と期限を登録し、残り日数を表示
- 期間内の土日・日本の祝日を重複なしで集計
- TODOの追加、完了チェック、削除
- スマートフォンではスワイプ、PCでは削除ボタンからTODOを削除
- 各TODOの達成度を`0 / 25 / 50 / 75 / 100%`の5段階で記録
- 各TODOの達成度から、目標全体の達成度を自動計算
- 初めて使う人向けの使い方チュートリアル
- localStorageによる端末内保存
- PWAとしてホーム画面へ追加でき、アプリ本体はオフラインでも利用可能

## 使い方

1. 「目標」から目標名と期限を設定します。
2. 期限までに必要な作業をTODOへ追加します。
3. 各TODOのスライダーで現在の達成度を更新します。
4. 完了したTODOにチェックを付けます。
5. 不要なTODOは、スマートフォンでは右スワイプ、PCでは削除ボタンから削除します。

画面上部には、期限までの残り日数、休日数、TODO全体から算出した目標達成度が表示されます。

## 達成度の計算

各TODOの5段階を内部では`0〜4`として保存し、その平均値をパーセントへ変換します。

```text
全体達成度 = round((TODOごとの段階値の合計 / TODO件数) × 25)
```

たとえば、3件のTODOが`25%・75%・100%`の場合、全体達成度は`67%`です。TODOがない場合は`0%`として表示します。完了チェックと達成度は別々に管理されます。

## 休日データ

日本の祝日は[national-holidays.jp](https://national-holidays.jp/about.html)からオンライン時に取得します。

- 期限に関係する年だけ取得
- 保存するのは祝日の日付のみ
- 年単位でlocalStorageへキャッシュ
- キャッシュの有効期間は30日
- 土日と祝日が重なる場合は1日として集計
- オフライン時は取得済みキャッシュを使用
- 利用可能なキャッシュがない場合は「休日データ未取得」と表示

## データとプライバシー

目標、TODO、達成度はブラウザのlocalStorageに保存され、アプリのサーバーには送信されません。祝日数を計算する際のみ、対象年を指定して祝日APIへアクセスします。

ブラウザのサイトデータを削除すると、保存した目標とTODOも削除されます。現時点では端末間同期やバックアップ機能はありません。

## デプロイ

Cloudflare WorkersのGit連携では、Production branchを`main`、Build commandを`npm run build`、Deploy commandを`npm run deploy:worker`に設定します。`wrangler.jsonc`は既存Worker名`deadlineapp`で`dist`をStatic Assetsとして配信するため、公開URLは`https://deadlineapp.zuiken2022robo.workers.dev/`のルートで動作します。Cloudflare側では環境変数`DEPLOY_BASE_PATH`を設定しません。これにより、JavaScript・マニフェスト・PWAの起動URLはすべて`/`を参照します。[Workers Buildsの設定](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/)と[Static Assets](https://developers.cloudflare.com/workers/static-assets/)に沿った構成です。

GitHub Pagesへの既存の自動デプロイも維持します。GitHub Actionsのビルド時だけ`DEPLOY_BASE_PATH=/DeadlineApp/`を指定し、リポジトリのサブパスに合わせます。Cloudflare WorkerとGitHub Pagesはいずれも`main`へのpushで再ビルドされます。Cloudflareでの最初のデプロイ後は、ページ本体に加えて`/assets/`配下のJSと`/manifest.webmanifest`が正しい形式で返ることを確認してください。

通常の開発フローは次のとおりです。

1. `main`から作業ブランチを作成
2. 実装後に`npm run lint`と`npm run build`を実行
3. Pull Requestを作成
4. `main`へマージ
5. Cloudflare WorkersとGitHub Actionsで自動デプロイ

## 今後の開発・公開計画（提案）

以下は**実装済み機能ではなく、次のPull Request以降の設計案**です。まず既存機能の安定性とデータ保護を確認し、計測の基準を作ってからページ数による進捗管理を追加します。どちらの機能も、利用者が目標を立て、少しずつ進み、また戻って来られるかを判断するために進めます。

### 1. Google Analytics 4：何を知りたいかから決める

目的は単なるアクセス数の増加ではありません。「初回訪問 → 目標設定 → TODO追加 → 進捗更新 → 再訪問」のどこで使いにくくなるかを見つけ、改善につなげます。このPWAはWebサイトとして配信されるため、GA4では**Webデータストリーム**を使います。Webの初回訪問は自動収集される`first_visit`で確認し、ネイティブアプリ向けの`first_open`を独自送信しません。`page_view`、`session_start`、`user_engagement`も自動収集に任せ、重複送信を避けます。ホーム画面に追加したPWAからの起動も同じWebサイトとして扱います。詳しくは[GA4の自動収集イベント](https://support.google.com/analytics/answer/9234069)と[イベント設定](https://developers.google.com/analytics/devguides/collection/ga4/events)を参照してください。

**イベントの契約案**：画面を開いただけ、入力を始めただけでは「設定した」と数えません。保存に成功し、アプリの状態が変わった時に1回送ります。スライダー操作やページ数入力は途中の値を送らず、指を離す・キーボードで確定する・編集シートで保存する時だけ送ります。全ての独自イベントに`schema_version: 1`を付け、後から定義を変えた場合に比較できるようにします。

| イベント | 送信タイミング | 送る項目（例） | 分かること |
| --- | --- | --- | --- |
| `first_visit`（自動） | 計測に同意したブラウザでの初回訪問 | GA4の標準項目のみ | 新規訪問者数の目安。ページ表示回数とは区別する |
| `session_start`（自動） | GA4がセッション開始と判定した時 | GA4の標準項目のみ | 再訪問と流入元の傾向 |
| `goal_set` | 空の状態から目標名と期限の保存に成功した時 | `deadline_bucket`: `d0_7` / `d8_30` / `d31_90` / `d91_plus` | 目標設定まで到達した人数と回数 |
| `goal_edited` | 既存の目標または期限を変更して保存した時 | `changed_field`: `title` / `deadline` / `both` | 設定の見直しが必要になる頻度 |
| `todo_added` | TODOの追加保存に成功した時 | `progress_mode`: `steps` / `pages`、`todo_count_bucket`: `n1` / `n2_3` / `n4_7` / `n8_plus` | 具体的な行動まで落とし込めたか |
| `progress_saved` | TODOの進捗を前回と異なる値で確定した時 | `progress_mode`、`progress_bucket`: `p0` / `p1_24` / `p25_49` / `p50_74` / `p75_99` / `p100` | 実際に進捗記録が使われているか |
| `todo_checked` / `todo_unchecked` | 完了チェックの状態が変わった時 | なし | 完了・やり直し操作の利用状況 |
| `tutorial_started` / `tutorial_completed` | ガイド開始／最終ステップ完了時 | なし | 初回案内が役立っているか |

送信は同意済み・オンライン・本番環境で、保存が確定した後に共通関数から`gtag('event', ...)`を呼ぶ形にします。たとえば期限が20日後の目標を初めて保存した場合は、本文や日付を含めず`gtag('event', 'goal_set', { deadline_bucket: 'd8_30', schema_version: 1 })`を1回送ります。端末への保存に失敗した場合は成功イベントに数えず、利用者へ保存できなかったことを知らせる設計にします。

`goal_set`は**目標の新規作成**だけ、`goal_edited`は既存目標の変更だけと定義します。現状は端末ごとに目標を1件保存する設計なので、`goal_set`のイベント数は「計測できた端末で新規に設定した回数」であり、「全世界で作られた目標の総数」や「実人数」とは一致しません。`todo_added`も追加した件数であって、ユニークな利用者数ではありません。削除や進捗の戻しは必要になってから追加し、最初からイベントを増やしすぎない方針です。

**見る指標と判断の仕方**

| 指標 | 定義 | 改善への使い方 |
| --- | --- | --- |
| 初回到達 | `first_visit`のユーザー数 | 公開後の新規流入を追う。計測同意者に限る |
| 目標設定率 | 初回訪問者のうち、同日中に`goal_set`したユーザーの割合 | 入力画面・期限設定の分かりにくさを探る |
| 初回の行動化率 | `goal_set`したユーザーのうち、同日中に`todo_added`した割合 | 目標から具体的なTODOへの導線を検証する |
| 進捗記録率 | `todo_added`したユーザーのうち、7日以内に`progress_saved`した割合 | 進捗UIが使いやすいかを検証する |
| 再訪率 | 初回訪問日の翌日から7日以内・28日以内に再訪したユーザーの割合 | 継続利用の傾向を見る。流入元と利用端末で分けて確認する |
| ページ機能利用率 | `todo_added`のうち`progress_mode=pages`の割合、およびページモード利用者の進捗記録率 | ページ入力が実際の用途に合うかを見る |

GA4のファネル探索やコホート分析では**イベント数ではなくユーザー数**を使い、期間・順序・同意条件を固定して比較します。新機能の前後比較では公開前後の流入元や利用端末の違いも確認し、少数のデータだけで成功と断定しません。イベントの追加パラメータは、GA4のレポートで使うものだけ[カスタム定義](https://support.google.com/analytics/answer/14240153)に登録します。実装時は[DebugViewとRealtime](https://developers.google.com/analytics/devguides/collection/ga4/troubleshoot)で、保存時に1回だけ送られることを確認します。

**送信範囲と利用者への説明**

- 目標名、TODO本文、入力したページ番号、正確な期限、端末内の保存データ、入力中の値は送信しない。ページ数や達成率は、分析に必要な場合も上表の区分値だけを送る。
- 計測は任意の同意を得た後に開始し、設定画面からいつでも変更できるようにする。拒否・未選択ならGoogleのタグ自体を読み込まず、イベントも送らない。これはGoogleが説明する[基本の同意モード](https://developers.google.com/tag-platform/security/concepts/consent-mode)に沿う案。`analytics_storage=denied`だけを設定する高度な同意モードは、Cookieなしの信号が送信され得るため、この方針とは異なる。
- 利用目的、送信先、送信するイベントの種類、同意の撤回方法を公開ページとアプリ内に明記する。URLや画面タイトルに利用者の入力内容を混ぜず、ページURLのクエリも確認する。GA4の拡張計測で不要なフォーム操作やサイト内検索を収集しない設定にする。[GA4の個人識別情報に関する指針](https://support.google.com/analytics/answer/6366371)も実装時に確認する。
- ローカル開発、プレビュー、テスト操作は本番プロパティに送らない。PWAがオフラインの間は分析のための送信待ちキューを新設せず、アプリの操作を妨げない。
- 同意しなかった人、分析ブロッカーを使う人、オフライン利用分はGA4に現れない。したがって`first_visit`は「アプリを初めて開いた全員」ではなく「計測できた初回訪問者」として扱う。
- 初回の同意選択は利用開始前に提示するが、拒否してもアプリは使えるようにする。同意前の操作は後からGA4へ補送しないため、途中から同意した人の導入ファネルは欠け得ることを分析時に明記する。

実装は「プライバシー説明と同意UI → GA4のWebストリームと送信窓口 → 上表のイベント → DebugViewで検証 → 公開後に指標を確認」の順で、独立したPull Requestにします。GA4の測定IDは公開用の設定値として管理し、アプリ内に秘密鍵やMeasurement ProtocolのAPIシークレットを置きません。送信処理を1か所に集約し、同意状態、開発環境、オフライン状態をそこで判定します。公開直後のデータを基準として残し、後述のページ機能の影響を比較します。

### 2. ページ数で達成率を記録する：一覧を広げず編集画面を使う

現在の5段階評価は読書・問題集には粗い一方、すべてのTODOがページ作業ではありません。**TODOごとに「5段階」か「ページ数」を選ぶ**設計を推奨します。既存TODOは5段階のまま保持し、ページ作業だけ切り替えられるようにします。Appleの[Disclosure controlsの指針](https://developer.apple.com/design/human-interface-guidelines/disclosure-controls)が示すように、詳細設定は必要な時だけ開ける構造にします。

スマートフォンの一覧行は、現在の左右の境界を保ちます。左側はチェックとTODO名、右側は`30%`、細い進捗バー、`30/100ページ`のような短い表示だけにします。狭い画面では右側を2行にし、バーの幅を優先します。右側全体をタップすると下から編集シートが開きます。**数字の入力欄や範囲変更欄を一覧行に置かない**ことで、320px程度の幅や文字拡大でも操作できるようにします。ページ範囲はシート内でいつでも変更でき、一覧から編集画面を探し回る必要はありません。

```text
一覧：  [○ 参考書を進める] │ [30%  ━━━────  30/100ページ]
                         ↓ 右側をタップ
シート： 開始ページ [10]   終了ページ [109]
         この範囲は 100ページ
         読み終えたページ数 [30]
         10〜39ページまで完了 / 30%  ━━━────
         [保存]
```

新しいTODOを作る時はまず名前を入力し、進捗方法の選択を追加します。「ページ数」を選んだ場合にだけ開始・終了ページを表示します。後からTODOの進捗欄を開けば、範囲・記録方法・進捗を編集できます。ページ数を使わないTODOは従来どおり5段階で操作します。新規のページTODOは0ページから始めます。既存TODOの記録方法を切り替える場合は、新しい方法での進捗を自分で入力・選択してもらい、前後の値と変更内容を保存前に示します。異なる方法の値を黙って換算しません。

**計算と入力ルール案**

```text
総ページ数 = 終了ページ - 開始ページ + 1  （両端を含む）
ページTODOの達成率 = round(読み終えたページ数 / 総ページ数 × 100)
5段階TODOの達成率 = 段階値 × 25
目標全体の達成率 = round(TODOごとの達成率の合計 / TODO件数)
```

開始・終了は1以上の整数で`開始 <= 終了`、読み終えたページ数は`0〜総ページ数`です。たとえば10〜109ページなら総数は100ページ、30ページ読了で30%かつ「39ページまで完了」です。`0ページ`なら「未着手」と表示します。ページ数を使うTODOと5段階TODOを混在させても、**TODO 1件を1票として平均**します。長い本1件だけで目標全体の達成率を支配させないためです。たとえば30%のページTODOと75%の5段階TODOなら、全体は`round((30 + 75) / 2) = 53%`です。TODOが0件なら0%。完了チェックは現在と同じく達成率とは別の状態として保ちます。

範囲の変更で既存の進捗が新しい意味に変わるため、開始・終了ページを編集する時は変更後の総数と達成率を**保存前にプレビュー**します。初期案では変更時に読了ページ数を明示的に入力し直してもらい、勝手な換算や切り捨てを避けます。範囲外の値、空欄、小数、逆順は保存不可として入力欄の近くに理由を表示します。入力にはスマートフォンの数字キーボードを使い、画面読み上げでは「30/100ページ、30%」と伝わるラベルを用意します。

保存データは進捗方法を判別できる形に拡張します。既存の`progress: 0〜4`は読み込み時に5段階モードへ移行し、すでに記録された値と完了チェックを維持します。計算は表示・保存・集計で共通の関数にまとめ、`開始=終了`、0ページ、最終ページ、混在、範囲編集、旧データ読み込みを確認します。シートは小型Android、iPhone、PC、ダークモード、文字拡大、キーボード表示、オフラインで操作を検証します。

実装は「計算とデータ移行 → 一覧と編集シート → 使い方ガイド更新 → 回帰確認」のまとまりでPull Requestにします。GA4が先に公開されていれば、ページモードの選択と進捗保存を上表の`progress_mode`で比較できます。

### 3. 継続して使われるための公開準備と運用

| 公開前 | JSONのエクスポート・インポート、全データ削除を用意する | 機種変更やブラウザデータ削除に備えられ、利用者が自分でデータを持ち出せる |
| 公開前 | プライバシー説明、問い合わせ先、更新履歴、既知の制約を公開する | 保存先と外部送信先が利用前に分かり、問題を報告できる |

| 初期公開 | 「誰向けか」を一文で伝える紹介ページ、スマホ画面、30秒程度の使い方例を用意する | 初めて見た人が「期限から逆算して進捗を記録するアプリ」と理解できる |
| 初期公開 | 少人数に1週間使ってもらい、目標設定・TODO追加・進捗更新を観察する | 分かりにくい箇所を操作例とともに記録できる |

最初の利用者像は「資格試験・読書・学習など、期限とページ範囲が決まった作業を少しずつ進める人」と置きます。いくつかの具体例で初回操作を試し、ページ数入力が本当に継続に役立つか確かめます。利用者を増やす前にバックアップと不具合報告の導線を整えることを優先します。

その後の候補は、TODOの編集・並べ替え、期限前の通知、複数目標、任意の端末間同期です。通知は許可を求める時期と頻度を小さく試し、同期は端末内保存だけでは困る声が十分に集まってから検討します。加重達成率も、実際に「TODOを同じ重みで平均すると困る」例が確認できた場合に設計します。機能数よりも、保存した計画を安心して続けられることを判断基準にします。
