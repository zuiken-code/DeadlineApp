# 期限くん

期限から逆算して、目標までにやることと進み具合を管理するモバイルファーストのPWAです。

Appleの[Human Interface Guidelines](https://developer.apple.com/jp/design/human-interface-guidelines/)を参考に、迷わず使えるシンプルな画面と、メインカラー`#26A79A`で設計しています。

**公開版:** [https://deadlineapp.zuiken.workers.dev/](https://deadlineapp.zuiken.workers.dev/)

## 主な機能

- 目標名と期限を登録し、残り日数を表示
- 期間内の土日・日本の祝日を重複なしで集計
- TODOの追加、完了チェック、削除
- スマートフォンではスワイプ、PCでは削除ボタンからTODOを削除
- TODOごとに開始・終了・現在ページを記録し、達成率を自動計算
- 各TODOの達成度から、目標全体の達成度を自動計算
- 初回の同意選択後に始まる使い方チュートリアル（設定から再確認可能）
- localStorageによる端末内保存
- PWAとしてホーム画面へ追加でき、アプリ本体はオフラインでも利用可能
- 設定画面から通知時刻を選び、目標までの残り日数をWeb Pushで毎日通知
- 任意の同意後に限り、Google Analytics 4で匿名化した利用イベントを計測

## 使い方

初回アクセスでは利用状況データの同意を選ぶと、矢印付きのチュートリアルが始まります。途中でスキップでき、後から「使い方」で再確認できます。チュートリアルはホーム画面への追加方法と通知の設定も案内します。

1. 「目標」から目標名と期限を設定します。
2. 期限までに必要な作業をTODOへ追加します。
3. TODOの編集ボタンから、開始ページと終了ページを設定します。
4. 一覧の「現在ページ」を更新すると、TODOと目標全体の達成度が自動計算されます。
5. 完了したTODOにチェックを付けます。
6. 不要なTODOは、スマートフォンでは右スワイプ、PCでは削除ボタンから削除します。
7. 必要に応じてホーム画面へアプリを追加します。対応ブラウザではチュートリアルからインストールを始められます。iPhone・iPadではSafariの共有メニューから「ホーム画面に追加」を選びます。
8. 目標設定後、ホームの案内か下部の「設定」から期限リマインダーをオンにします。通知時刻は設定から変更できます。

画面上部には、期限までの残り日数、休日数、TODO全体から算出した目標達成度が表示されます。通知がオフのときは、目標カードの下に通知の案内が表示されます。通知の許可は利用者が「通知をオン」を押したときに求めます。iPhone・iPadでWeb Pushを使うには、ホーム画面に追加したアプリから開く必要があります。

## 達成度の計算

開始ページと終了ページは両端を含めて計算します。現在ページは、そのページまで完了したものとして扱います。

```text
総ページ数 = 終了ページ - 開始ページ + 1
完了ページ数 = 現在ページ - 開始ページ + 1
TODOの達成度 = round(完了ページ数 / 総ページ数 × 100)
目標全体の達成度 = round(TODOごとの達成度の合計 / TODO件数)
```

たとえば10〜109ページを設定し、現在ページが39なら、30/100ページで達成度は`30%`です。現在ページが空欄なら未着手の`0%`として扱います。TODOがない場合も`0%`です。完了チェックと達成度は別々に管理されます。

## 休日データ

日本の祝日は[national-holidays.jp](https://national-holidays.jp/about.html)からオンライン時に取得します。

- 期限に関係する年だけ取得
- 保存するのは祝日の日付のみ
- 年単位でlocalStorageへキャッシュ
- キャッシュの有効期間は30日
- 土日と祝日が重なる場合は1日として集計
- オフライン時は取得済みキャッシュを使用
- 利用可能なキャッシュがない場合は「休日データ未取得」と表示

## データとプライバシー

目標、TODO、達成度は通常ブラウザのlocalStorageに保存されます。祝日数を計算する際のみ、対象年を指定して祝日APIへアクセスします。

期限リマインダーをオンにした場合に限り、Web Push配信に必要な購読情報、目標名、期限、通知時刻、端末のタイムゾーンをCloudflare KVへ保存します。TODO、ページ数、達成度は通知サーバーへ送りません。通知をオフにするとKVの登録情報を削除し、無効になった購読情報も配信時に自動削除します。

Google Analyticsは初回の確認で同意した場合に限り読み込みます。目標設定、TODO追加、進捗更新、完了チェック、チュートリアルの利用状況を区分値として送信しますが、目標名、TODO本文、入力したページ番号、正確な期限は送信しません。設定画面の「利用状況の共有」からいつでも停止・再開できます。ローカル開発、Cloudflareのプレビュー、オフライン操作では送信しません。したがってGA4で見える人数やイベント数は、同意した利用者・オンラインで計測できた利用者の範囲に限られ、全利用者の実数とは一致しません。

ブラウザのサイトデータを削除すると、保存した目標とTODOも削除されます。現時点では端末間同期やバックアップ機能はありません。

## デプロイ

Cloudflare WorkersのGit連携では、Production branchを`main`、Build commandを`npm run build`、Deploy commandを`npm run deploy:worker`に設定します。`wrangler.jsonc`は既存Worker名`deadlineapp`で`dist`をStatic Assetsとして配信するため、公開URLは`https://deadlineapp.zuiken.workers.dev/`のルートで動作します。Cloudflare側では環境変数`DEPLOY_BASE_PATH`を設定しません。これにより、JavaScript・マニフェスト・PWAの起動URLはすべて`/`を参照します。[Workers Buildsの設定](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/)と[Static Assets](https://developers.cloudflare.com/workers/static-assets/)に沿った構成です。

GitHub Pagesへの既存の自動デプロイも維持します。GitHub Actionsのビルド時だけ`DEPLOY_BASE_PATH=/DeadlineApp/`を指定し、リポジトリのサブパスに合わせます。Cloudflare WorkerとGitHub Pagesはいずれも`main`へのpushで再ビルドされます。Cloudflareでの最初のデプロイ後は、ページ本体に加えて`/assets/`配下のJSと`/manifest.webmanifest`が正しい形式で返ることを確認してください。

通常の開発フローは次のとおりです。

1. `main`から作業ブランチを作成
2. 実装後に`npm run lint`と`npm run build`を実行
3. Pull Requestを作成
4. `main`へマージ
5. Cloudflare WorkersとGitHub Actionsで自動デプロイ

### Web Push通知のCloudflare設定

通知機能はコードのデプロイに加えて、Cloudflare Dashboardで次の初期設定が必要です。設定が終わるまではアプリ本体を通常どおり利用でき、設定画面の通知だけが「準備が必要」と表示されます。

1. **KV Namespaceを作る**
   - Cloudflare Dashboard → Storage & databases → KV → Create
   - Namespace名の例：`DEADLINE_PUSH_SUBSCRIPTIONS`
2. **WorkerへKVを接続する**
   - Workers & Pages → `deadlineapp` → Settings → Bindings
   - KV Namespace bindingを追加
   - Variable name：`SUBSCRIPTIONS`（大文字を含めて完全一致）
   - KV namespace：手順1で作成したもの
3. **VAPID鍵を生成する**

   ```bash
   npx web-push generate-vapid-keys
   ```

4. **Workerへ変数とSecretを追加する**
   - `VAPID_PUBLIC_KEY`：生成されたPublic Key（通常の変数）
   - `VAPID_PRIVATE_KEY`：生成されたPrivate Key（Secretとして暗号化）
   - `VAPID_SUBJECT`：`https://deadlineapp.zuiken.workers.dev/`（通常の変数）
   - `wrangler.jsonc`の`keep_vars: true`により、Gitデプロイ後もダッシュボードで設定した変数を保持
5. **最新デプロイを確認する**
   - `wrangler.jsonc`の`*/15 * * * *`によりCronが15分ごとに実行される
   - Settings → TriggersでCron Triggerが作成されていることを確認
   - 必要ならProductionを再デプロイ
6. **実機で登録する**
   - 目標と期限を設定
   - 設定 → 期限リマインダーをオン
   - Androidは通知を許可。iPhone/iPadはiOS 16.4以降でホーム画面へ追加したPWAから許可

VAPID Private Keyはリポジトリ、Pull Request、通常の環境変数へ記載しません。鍵を再生成すると既存購読へ送信できなくなるため、漏えい時以外は同じ鍵を保持します。Cronは各購読のタイムゾーンと設定時刻を照合し、期限当日までは「残り0日」を含めて送信し、期限を過ぎた登録は削除します。OSの省電力設定やPushサービスの状態により、通知は設定時刻から遅れる場合があります。

## 今後の開発・公開計画（提案）

以下は実装済み機能の計測基準と、今後の公開・改善計画です。利用者が目標を立て、少しずつ進み、また戻って来られるかを判断するために使います。

### 1. Google Analytics 4：何を知りたいかから決める（実装済み）

目的は単なるアクセス数の増加ではありません。「初回訪問 → 目標設定 → TODO追加 → 進捗更新 → 再訪問」のどこで使いにくくなるかを見つけ、改善につなげます。このPWAはWebサイトとして配信されるため、GA4では**Webデータストリーム**を使います。Webの初回訪問は自動収集される`first_visit`で確認し、ネイティブアプリ向けの`first_open`を独自送信しません。`page_view`、`session_start`、`user_engagement`も自動収集に任せ、重複送信を避けます。ホーム画面に追加したPWAからの起動も同じWebサイトとして扱います。詳しくは[GA4の自動収集イベント](https://support.google.com/analytics/answer/9234069)と[イベント設定](https://developers.google.com/analytics/devguides/collection/ga4/events)を参照してください。

**イベントの契約**：画面を開いただけ、入力を始めただけでは「設定した」と数えません。保存に成功し、アプリの状態が変わった時に1回送ります。ページ数入力は途中の値を送らず、フォーカスを外す・Enterで確定する・編集シートで保存する時だけ送ります。全ての独自イベントに`schema_version: 1`を付け、後から定義を変えた場合に比較できるようにします。

| イベント | 送信タイミング | 送る項目（例） | 分かること |
| --- | --- | --- | --- |
| `first_visit`（自動） | 計測に同意したブラウザでの初回訪問 | GA4の標準項目のみ | 新規訪問者数の目安。ページ表示回数とは区別する |
| `session_start`（自動） | GA4がセッション開始と判定した時 | GA4の標準項目のみ | 再訪問と流入元の傾向 |
| `goal_set` | 空の状態から目標名と期限の保存に成功した時 | `deadline_bucket`: `d0_7` / `d8_30` / `d31_90` / `d91_plus` | 目標設定まで到達した人数と回数 |
| `goal_edited` | 既存の目標または期限を変更して保存した時 | `changed_field`: `title` / `deadline` / `both` | 設定の見直しが必要になる頻度 |
| `todo_added` | TODOの追加保存に成功した時 | `progress_mode`: `steps` / `pages`、`todo_count_bucket`: `n1` / `n2_3` / `n4_7` / `n8_plus` | 具体的な行動まで落とし込めたか |
| `progress_saved` | TODOの進捗を前回と異なる値で確定した時 | `progress_mode`、`progress_bucket`: `p0` / `p1_24` / `p25_49` / `p50_74` / `p75_99` / `p100` | 実際に進捗記録が使われているか |
| `todo_checked` / `todo_unchecked` | 完了チェックの状態が変わった時 | なし | 完了・やり直し操作の利用状況 |
| `tutorial_started` / `tutorial_completed` | ガイド開始／最終ステップ完了時 | なし | 初回案内が役立っているか |

送信は同意済み・オンライン・本番環境で、保存が確定した後に共通関数から`ReactGA.event(...)`を呼ぶ形にします。たとえば期限が20日後の目標を初めて保存した場合は、本文や日付を含めず`ReactGA.event('goal_set', { deadline_bucket: 'd8_30', schema_version: 1 })`を1回送ります。端末への保存に失敗した場合は成功イベントに数えず、利用者へ保存できなかったことを知らせる設計にします。

`goal_set`は**目標の新規作成**だけ、`goal_edited`は既存目標の変更だけと定義します。現状は端末ごとに目標を1件保存する設計なので、`goal_set`のイベント数は「計測できた端末で新規に設定した回数」であり、「全世界で作られた目標の総数」や「実人数」とは一致しません。`todo_added`も追加した件数であって、ユニークな利用者数ではありません。削除や進捗の戻しは必要になってから追加し、最初からイベントを増やしすぎない方針です。

**見る指標と判断の仕方**

| 指標 | 定義 | 改善への使い方 |
| --- | --- | --- |
| 初回到達 | `first_visit`のユーザー数 | 公開後の新規流入を追う。計測同意者に限る |
| 目標設定率 | 初回訪問者のうち、同日中に`goal_set`したユーザーの割合 | 入力画面・期限設定の分かりにくさを探る |
| 初回の行動化率 | `goal_set`したユーザーのうち、同日中に`todo_added`した割合 | 目標から具体的なTODOへの導線を検証する |
| 進捗記録率 | `todo_added`したユーザーのうち、7日以内に`progress_saved`した割合 | 進捗UIが使いやすいかを検証する |
| 再訪率 | 初回訪問日の翌日から7日以内・28日以内に再訪したユーザーの割合 | 継続利用の傾向を見る。流入元と利用端末で分けて確認する |
| ページ機能利用率 | `todo_added`のうち`progress_mode=pages`の割合、およびページモード利用者の進捗記録率 | ページ入力が実際の用途に合うかを見る |

GA4のファネル探索やコホート分析では**イベント数ではなくユーザー数**を使い、期間・順序・同意条件を固定して比較します。新機能の前後比較では公開前後の流入元や利用端末の違いも確認し、少数のデータだけで成功と断定しません。イベントの追加パラメータは、GA4のレポートで使うものだけ[カスタム定義](https://support.google.com/analytics/answer/14240153)に登録します。実装時は[DebugViewとRealtime](https://developers.google.com/analytics/devguides/collection/ga4/troubleshoot)で、保存時に1回だけ送られることを確認します。

**送信範囲と利用者への説明**

- 目標名、TODO本文、入力したページ番号、正確な期限、端末内の保存データ、入力中の値は送信しない。ページ数や達成率は、分析に必要な場合も上表の区分値だけを送る。
- 計測は任意の同意を得た後に開始し、設定画面からいつでも変更できるようにする。拒否・未選択ならGoogleのタグ自体を読み込まず、イベントも送らない。これはGoogleが説明する[基本の同意モード](https://developers.google.com/tag-platform/security/concepts/consent-mode)に沿った実装。`analytics_storage=denied`だけを設定する高度な同意モードは、Cookieなしの信号が送信され得るため、この方針とは異なる。
- 利用目的、送信先、送信するイベントの種類、同意の撤回方法を公開ページとアプリ内に明記する。URLや画面タイトルに利用者の入力内容を混ぜず、ページURLのクエリも確認する。GA4の拡張計測で不要なフォーム操作やサイト内検索を収集しない設定にする。[GA4の個人識別情報に関する指針](https://support.google.com/analytics/answer/6366371)も実装時に確認する。
- ローカル開発、プレビュー、テスト操作は本番プロパティに送らない。PWAがオフラインの間は分析のための送信待ちキューを新設せず、アプリの操作を妨げない。
- 同意しなかった人、分析ブロッカーを使う人、オフライン利用分はGA4に現れない。したがって`first_visit`は「アプリを初めて開いた全員」ではなく「計測できた初回訪問者」として扱う。
- 初回の同意選択は利用開始前に提示するが、拒否してもアプリは使えるようにする。同意前の操作は後からGA4へ補送しないため、途中から同意した人の導入ファネルは欠け得ることを分析時に明記する。

ReactGAを送信窓口として使い、同意状態、開発環境、公開ホスト、オンライン状態を`analytics.ts`で一括判定します。測定IDは公開用の設定値として管理し、アプリ内に秘密鍵やMeasurement ProtocolのAPIシークレットを置きません。公開後はRealtimeとDebugViewで重複送信がないことを確認し、初期データを今後の改善基準として残します。

### 2. ページ数で達成率を記録する（実装済み）

TODOの編集ボタンから名前、開始ページ、終了ページ、現在ページを設定できます。一覧では現在ページだけをすぐに更新でき、TODOごとのパーセント、進捗バー、目標全体の達成度へ即時反映します。

既存データは削除せず、ページ範囲を設定するまでは以前の5段階の値を達成率表示に使用します。ページ範囲を保存したTODOからページ方式へ切り替わります。開始・終了・現在ページは1以上の整数で検証し、範囲変更後の達成率を保存前に確認できます。

最初の利用者像は「資格試験・読書・学習など、期限とページ範囲が決まった作業を少しずつ進める人」と置きます。いくつかの具体例で初回操作を試し、ページ数入力が本当に継続に役立つか確かめます。利用者を増やす前にバックアップと不具合報告の導線を整えることを優先します。

その後の候補は、TODOの編集・並べ替え、期限前の通知、複数目標、任意の端末間同期です。通知は許可を求める時期と頻度を小さく試し、同期は端末内保存だけでは困る声が十分に集まってから検討します。加重達成率も、実際に「TODOを同じ重みで平均すると困る」例が確認できた場合に設計します。機能数よりも、保存した計画を安心して続けられることを判断基準にします。
